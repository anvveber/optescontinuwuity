## Details

### 1. Websites can query the server through the relay (tested, server side)

- The relay listens on `127.0.0.1:8008`. The server answered every origin with
  `Access-Control-Allow-Origin: *`.
- Without login, `/_matrix/client/v1/auth_metadata` returned the server name.
  A page in the user's normal browser could read it: this visitor is a member
  of this server.
- The same page could test user names (`/register/available`) and try
  passwords.
- Not tested in a browser. Some browsers ask before a website may talk to
  127.0.0.1; that is not a defence to rely on.

Fix: `restrict_request_hosts`, `allowed_origins`, OAuth off. See `hardening.md`.

### 2. Front list could make relays leave Tor (tested)

- The relay accepted transport `tcp` ("tests only") and dialled the address
  directly.
- The list-signing key is on the core (weekly re-sign). The VPS host can read
  it, sign such a list, and get every user's IP address.

Fix: relays dial only `<56 chars>.onion` (tor) and `<52 chars>.b32.i2p` (i2p)
addresses. `tcp` exists only in builds with the cargo feature `test-fronts`.
`optes-keys sign-list` applies the same rule.

Still true: the key is on the core, so the host can publish its own *onion*
fronts. That gives it nothing it doesn't have. Signing lists offline would
remove even that, but then the weekly renewal must be done by hand.

### 3. Personal details in a public repository

The design documents contained details about the operator's own devices and
setup. They were removed, and the history of this repository was rewritten on
2026-11-10 so that earlier commits no longer contain them. Rule from now on:
nothing about a particular operator or deployment goes into this repository
(`HANDOFF.md` §7).

A rewrite does not reach copies that already exist: clones, and commits a
hosting service still keeps by hash until it cleans up.

### 4. End-to-end encryption and an active host

The homeserver decides which devices an account has and who is in a room. A
host that controls it can add a device or a member and receive the keys for
future messages. Defences are in the clients only: verify devices, "never send
to unverified devices", watch member lists.

### 5. Handshake replay (tested)

Message 1 of Noise IK can be recorded by a front and sent again. The gateway
answered it, and stayed silent once the device was removed: a test for "is
this device still allowed". The spec said a prober learns nothing.

Fix: `HELLO` carries a counter; the gateway accepts only a counter higher than
the last one from that device (`phase2-protocol-spec.md` §3.1).

### 6. Compromised front and guard discovery

A front holds a key to the core's ingress onion. With a Tor client it controls
it can open any number of connections through rendezvous points it picks, the
starting point of a guard-discovery attack. Tor's vanguards-lite (default)
limits this; the full vanguards add-on is stronger and is not installed.

2026-11-15: accepted, not fixed. In Debian 13's Tor (0.4.9.15) vanguards-lite
follows the network's consensus and is on when the consensus says nothing
(manual). A core in a VM got a consensus without that parameter. The full add-on is not packaged in
Debian 13; it is not installed from elsewhere (handbook §4.6).

### 7. Open fronts

Without `add-client`, a front accepted connections from anyone who knew its
address. Each costs the core a Tor stream and reaches the gateway handshake.

Fix: `setup-front.sh install` makes a client key `relays` before Tor starts
and prints it once. `--open` keeps the old behaviour. I2P fronts have no client
authorization.

### 8. Logs

- The gateway logged "tunnel up/down" to the journal on disk.
- The relay logged front addresses and connect times to the user's journal.

Fix: gateway and relay units run with `RUST_LOG=warn`; the relay prints the
front address only at debug level; journald on core and fronts keeps logs in
memory only (`Storage=volatile`, old logs deleted); no core dumps
(`LimitCORE=0`, `kernel.core_pattern`).

Consequence: after a reboot there are no logs from before it.

### 9. Push tokens

Phone clients register a push token. The server can never use it (no network)
but stored it: a link from an account to a phone, on the core's disk.

Fix: `allow_pushers = false` (answer success, store nothing).

### 10. Level-2 windows and clocks

Each relay sent on multiples of the window by its own clock. A clock that is a
second off gives that device a stable offset a front can recognise. The core
has no time sync, so its grid could drift from the relays'.

Fix: `WELCOME` carries the gateway's time; relays align to it. Trade-off in
`phase2-protocol-spec.md` §4. Since 2026-11-15 core and fronts also set their
clock over Tor (`optes-clock.sh`, `HANDOFF.md` §4f).

### 11. Recognisable traffic

Bursts on exact 15 s multiples (level 2) or a flat 10 KB/s (level 3). An ISP
can tell that a line runs this software. Not fixed; now stated as a limitation.

### 12. Leaks around the relay

- Calls go direct (WebRTC/STUN). The server can't see or stop them in
  encrypted rooms.
- Integration managers get the user's Matrix ID through an OpenID token.
  Fix: `allow_openid_tokens = false`.
- Device names ("Element Desktop: Linux") are visible to other members.
  Fixed 2026-11-15: `show_device_names_to_others = false` (server option, set
  by `setup-core.sh`); other users see the device ID (`hardening.md`).

### 13. First SSH over clearnet

`setup-core.sh` and `setup-front.sh` are run over normal SSH first. The
provider sees the admin's IP address. Use `torsocks ssh` (or SSH over a VPN you
trust) for that first session too, and for the provider's web panel.

## Low items

- **L1** RocksDB marks deleted keys; the bytes stay in its files until
  compaction, and in any backup or disk snapshot. Clients also keep their own
  copies of messages. Since 2026-11-15 `setup-core.sh update` copies the whole
  database before it swaps the programs and deletes the copy afterwards; the
  copy's blocks stay in free disk space until overwritten.
  Fixed 2026-11-15 for the database files: after a purge the server flushes
  and compacts everything, and with retention on keeps no WAL archive and
  rewrites the MANIFEST after each change. Tested: no purged text and no
  purged ID outside kept events' `prev_events` in any file (`retention-design.md`).
- **L2** `install` no longer makes an ingress key. Make one per front:
  `setup-core.sh add-client <name>`.
- **L3** continuwuity's socket now belongs to group `matrix-sock` (gateway
  only) while port 80 is closed. `direct-ingress on` switches it to Tor's group
  and restarts continuwuity.
- **L4** Tor may attach several streams for the same onion to one circuit. The
  spec (§6) assumes one circuit per relay connection. Check with real Tor.
- **L5** No `update` command; no unattended upgrades over Tor. Fixed
  2026-11-15: `setup-core.sh update` and unattended-upgrades on core and
  fronts (`HANDOFF.md` §4g).
- **L6** `cargo audit` (2026-11-10): nothing for the tunnel. The server
  lockfile has upstream advisories (quinn-proto, rustls, rsa, pulldown-cmark,
  crypto-bigint, ctutils, libz-sys), mostly in network code this setup does
  not use. Analysed one by one on 2026-11-16/17: see "Dependency advisories"
  below.
- **L7** The kit binaries were built by hand. Since 2026-11-14 `make-kit.sh`
  builds them, with build paths, git remote and commit kept out. The last
  build paths (the server's embedded web pages) were removed on 2026-11-15
  (`HANDOFF.md` §4c). Still open: two builds of one commit on different
  machines were never compared, and nothing builds in CI.
- **L8** Tor enforces client authorization only while at least one client is
  listed. `remove-client` of the last key therefore opened the ingress onion
  (and a front's onion) to anyone who knew the address; so would an install
  without a first key. Fix: when no client is left, the scripts list a key
  whose private half is thrown away (`locked.auth`), so nothing can connect
  until the next `add-client`. The last admin key can't be removed.

### 14. Removal from any room through a space (tested)

- Auto-leave took the space's `m.space.child` events as the list of its
  rooms. Sending that event needs power in the space only (50 by default).
- Test: a moderator listed a private conversation between two other users as
  a child of the space, then removed one of them from the space. The server
  made that user leave the conversation. The room is invite-only, so the user
  could not get back in.
- A user who leaves the space on their own goes through the same code (read,
  not run).

Fix: a room counts as a child of a space only if the room names the space: an
`m.space.parent` event for it, or a restricted join rule that admits the
space's members. Both need power in the room itself. See `spaces.md`.

### 15. Members joined to rooms outside the space (tested)

Same cause, other direction. Listing a room joined every member of the space
to it, if they were allowed in: an open room anywhere on the server, or a room
they held an invitation to. A moderator could invite a member to a room and
accept for them.

Fixed by the same rule. Consequence: a room that already exists and is added
to a space with a client's "add existing room" is joined automatically only if
it names the space. Not tested with real clients.

### 16. make-space.py and proxies (tested)

Python uses `http_proxy` from the environment for every address, 127.0.0.1
included, unless `no_proxy` lists it. With such a variable set, the tool sent
the login request, with user name and password, to the proxy.

Fix: the tool never uses a proxy. The test scripts still follow the
environment; they only use throwaway accounts (`HANDOFF.md` §5: set
`no_proxy`).

### Low items

- **L9** `tunnel_e2e.py` checked "constant rate" (level 3) and "only at window
  boundaries" (level 2) in the idle seconds at the end of the run. A relay
  that sent data at once and kept the pattern only when idle would have
  passed. Now both are checked over the whole session, which includes a 60 KB
  transfer: level 3 stays at the fixed rate; level 2 sends nothing off the
  grid except the handshake (one frame each way when the connection opens).
  Level 1 (bursts padded to a power of two) was not checked on the wire:
  on one machine the bursts run into each other. The padding rule itself has a
  unit test.
  2026-11-18: level 1 is checked on the wire as far as one machine allows.
  After the session, six small requests 1.5 s apart; the recorded traffic is
  split into groups at gaps over 150 ms. Every group, each way, must be a
  whole number of padded bursts (a multiple of 4 frames). A check for single
  bursts (exactly a power of two) is not possible here: a request takes
  several bursts when the relay reads it in parts, and those merge in time.
  Control: a tunnel build without padding fails it (groups of 1-6 frames).
  Level 1 over real Tor is still not checked.
- **L10** Not tested anywhere (2026-11-14); each has a check since
  2026-11-18, with a control that shows the check can fail:
  - delayed release and retention through sliding sync (the tests use
    `/sync` v3, `/event`, `/messages`, `/context`, `/state`, search).
    Now: `delayed_release_e2e.py` checks sliding sync, initial and from a
    position taken before the send, before and after the tick (control:
    with release off the same request has the event at once);
    `retention_e2e.py` checks both after expiry (control: both have the
    messages before expiry).
  - retention in a sync that continues from an old token (only an initial
    sync is checked). Now: `/sync` from a token taken before the messages
    were sent (control: it has them before expiry).
  - spaces: that a profile change in a space does not re-join channels the
    user left (documented behaviour). Now in `spaces_e2e.py` (control: the
    new display name reaches the space; with the "real join only" rule
    removed from the server, the check fails).
  - browser guard: an `Origin` with the server's host and another port (the
    code compares host and port together). Now: the server's address with
    another port, and a listed origin with another port, are refused
    (control: with the guard off both are served).
- **L11** `test/home-test.sh` writes a server config without the browser guard,
  `allow_pushers`, `allow_openid_tokens` and the OAuth switch, opens plain HTTP
  on port 80 and logs to files. It was no longer the planned way to test.
  Removed on 2026-11-15: the test VMs (`test/vm.py`, `HANDOFF.md` §5) cover
  real Tor with the real setup scripts.
- `make-space.py` leaves what it created so far when a later step fails;
  there is no clean-up. Passing `--password` on the command line shows it in
  the process list; leave it out to be asked.

## Tests over real Tor, 2026-11-14

Core, relay and a Tor front each in a Debian 13 VM, all on the real Tor
network (`HANDOFF.md` §4e). Found:

| # | Finding | Severity | Done |
|---|---|---|---|
| 17 | `remove-client` does not cut off a client that already holds the onion's descriptor | medium | fixed (core and front scripts) |
| L12 | `setup-relay.sh front-auth` right after `install`: the key is not read | low | fixed |
| L13 | `setup-relay.sh install` again with another `--level` does not replace the running relay | low | fixed |

### 17. Revoked client keys keep working (tested)

- Tor's client authorization encrypts the onion's descriptor to the listed
  clients. It does not check the client again when it connects.
- `remove-client` removed the key and reloaded Tor. A reload keeps the
  introduction points. A client that had fetched the descriptor before
  could still connect: tested with the key of a removed relay, through
  Tor's SOCKS port to the core's ingress onion, minutes after the removal.
- For a burned front this means: after `remove-client <front>` it could
  keep reaching the core's ingress onion, the starting point of finding 6.

Fix: `remove-client` restarts Tor (from a systemd timer 3 s later, so it
also completes when the command is given over the admin onion). Tor then
picks new introduction points, which only listed clients can learn. Tested:
after the restart the removed client got "Client authorization for
requested onion address is invalid". Cost: every tunnel and admin SSH
session drops; other clients can need a few minutes to reconnect while
their cached descriptor is stale.

### Low items

- **L4** (from above) Tor put three streams from the front to the core's
  onion on one circuit. `phase2-protocol-spec.md` §6 now says so; what this
  shows to the core's guard is listed there.
- **L12** `front-auth` ran `systemctl reload tor`. On Debian this goes to
  `tor@default` and is lost while it is still starting, as it is right after
  `install`. The relay then never connected. `front-auth` now restarts Tor.
- **L13** `install` used `systemctl --user enable --now`, which leaves a
  running relay alone. It now restarts it.
- Not a finding, but worth knowing: the first connection to an onion from
  a Tor that has just started, or whose cached descriptor is stale, often
  takes longer than the relay's 120 s connect timeout. The relay retries
  with backoff; a later try worked every time. Slow in 6 of 17 relay
  starts, each time right after Tor (the relay's, the front's or the
  core's) had started or restarted.


## Found during the upstream move, 2026-11-17

| # | Finding | Severity | Done |
|---|---|---|---|
| 18 | Delayed release does not hide thread replies: the thread root's summary shows them before the tick | medium | fixed 2026-11-18 (server) |

### 18. Thread replies before the tick (tested)

- A thread reply updates the summary stored in the thread root's
  `unsigned` (`m.relations` → `m.thread`: count and latest reply) when it is
  sent. The release gate checks the event a client asks for, here the
  root, which is already released; the summary inside it is not checked.
- Test: release interval 15 s, a reply sent 1.5 s after a tick. Another
  member fetched the root with `/event` at once: the summary had the new
  count and the reply's content, while `/event` of the reply itself gave
  403. The same through `/messages`. So a member who polls the root learns
  when a reply was sent, to within their polling interval, instead of to
  within the window. On v26.9.1 the summary held the reply's content
  (ciphertext in an encrypted room); since v26.9.4 (upstream SEC39) also
  its sender and event ID. Its timestamp is the rounded one.
- Who can see it: members of the room only (the root's own visibility
  rules apply). Not someone outside the room.
- Also seen while fixing it: the thread list (`/threads`) listed the root
  at its first reply, before the tick; and a redaction in a thread rebuilt
  the summary from all replies, held ones included.

Fix (2026-11-18): while delayed release is on, a reply only queues its
thread update; the tick that releases the reply applies it (summary and
participants), before it wakes waiting clients. Summaries are rebuilt from
released replies only. Details: `delayed-release-spec.md` §10. Tested:
`run-e2e.sh` has new thread checks (summary through `/event` and
`/messages`, the thread list, a redaction while a reply is held); four of
them fail on the binary before the fix and pass after; with release off
the summary is updated at once, as upstream. A reply held when the server
stops is counted after the restart (by hand). Not tested: a crash with a
held reply (the summary then lacks it until the thread changes again).

## Dependency advisories (L6), 2026-11-17

`cargo audit` with the RustSec database of 2026-11-16 (1509 advisories), on
the server's `Cargo.lock` after the move to upstream v26.9.4, and on the
tunnel's. Tool and database live under `target/` (`cargo install
cargo-audit --locked --root target/tools`; `target/tools/bin/cargo-audit

has no network (`PrivateNetwork=yes`), so it never opens an outgoing
connection; federation is off; it listens on a unix socket only, without

`setup-core.sh`).

`make-kit.sh` builds (`cargo tree -p conduwuit -e normal,build` with the
default features).

**Tunnel:** no advisory, no warning.

**What the move to v26.9.4 itself fixed:** upstream's own security fixes
(SEC15, SEC31, SEC34, SEC36, SEC39 in v26.9.2; SEC45 in v26.9.4). Upstream
does not describe them; from the code:
- SEC31: `/event` returns 404 for an event that belongs to another room.
- SEC45: a redaction must be in the same room as the event it redacts
  (checked twice).
- SEC15: an event whose state the server never computed (outliers,
  backfill) is visible only to users joined to the room; before, to anyone
  who asked.
- SEC36: a key query keeps only the keys of the users and the server it
  asked about.
- SEC34: a membership event that claims a third-party invite is checked
  against the room's invite and its signature; before, the auth rules
  skipped that check.
- SEC39: a redacted thread reply no longer stays in the thread root's
  summary.

Upstream changed no dependency, no config key and no database format
between v26.9.1 and v26.9.4. One stored value changes form: a thread root's
summary (`unsigned` → `m.relations` → `m.thread` → `latest_event`) now
holds the whole latest reply (sender, event ID, time), before only its
content. Summaries written by the old server keep the old form until the
thread's next reply or redaction.
