# Privacy audit, 2026-11-10

Scope: the parts this fork adds. The tunnel (`tunnel/src`), the server patches
(diff against upstream v26.9.1), the three setup scripts, the design documents.

Not covered: `space_autojoin` line by line, the test scripts, `make-space.py`,
upstream continuwuity itself, anything over real Tor or I2P.

"Tested" means reproduced with the built binaries. Everything else comes from
reading code or documents.

## Details

### 1. Websites can query the server through the relay (tested, server side)

- The relay listens on `127.0.0.1:8008`. The server answered every origin with
  `Access-Control-Allow-Origin: *`.
- Without login, `/_matrix/client/v1/auth_metadata` returned the server name.
  A page in the user's normal browser could read it: this visitor is a member
  of this server.
- The same page could test user names (`/register/available`) and try
  passwords.
- Not tested in a browser. Some browsers ask before a website may talk to
  127.0.0.1; that is not a defence to rely on.

Fix: `restrict_request_hosts`, `allowed_origins`, OAuth off. See `hardening.md`.

### 2. Front list could make relays leave Tor (tested)

- The relay accepted transport `tcp` ("tests only") and dialled the address
  directly.
- The list-signing key is on the core (weekly re-sign). The VPS host can read
  it, sign such a list, and get every user's IP address.

Fix: relays dial only `<56 chars>.onion` (tor) and `<52 chars>.b32.i2p` (i2p)
addresses. `tcp` exists only in builds with the cargo feature `test-fronts`.
`optes-keys sign-list` applies the same rule.

Still true: the key is on the core, so the host can publish its own *onion*
fronts. That gives it nothing it doesn't have. Signing lists offline would
remove even that, but then the weekly renewal must be done by hand.

### 3. Personal details in a public repository

The design documents contained details about the operator's own devices and
setup. They were removed, and the history of this repository was rewritten on
2026-11-10 so that earlier commits no longer contain them. Rule from now on:
nothing about a particular operator or deployment goes into this repository
(`HANDOFF.md` §7).

A rewrite does not reach copies that already exist: clones, and commits a
hosting service still keeps by hash until it cleans up.

### 4. End-to-end encryption and an active host

The homeserver decides which devices an account has and who is in a room. A
host that controls it can add a device or a member and receive the keys for
future messages. Defences are in the clients only: verify devices, "never send
to unverified devices", watch member lists.

### 5. Handshake replay (tested)

Message 1 of Noise IK can be recorded by a front and sent again. The gateway
answered it, and stayed silent once the device was removed: a test for "is
this device still allowed". The spec said a prober learns nothing.

Fix: `HELLO` carries a counter; the gateway accepts only a counter higher than
the last one from that device (`phase2-protocol-spec.md` §3.1).

### 6. Compromised front and guard discovery

A front holds a key to the core's ingress onion. With a Tor client it controls
it can open any number of connections through rendezvous points it picks, the
starting point of a guard-discovery attack. Tor's vanguards-lite (default)
limits this; the full vanguards add-on is stronger and is not installed.

### 7. Open fronts

Without `add-client`, a front accepted connections from anyone who knew its
address. Each costs the core a Tor stream and reaches the gateway handshake.

Fix: `setup-front.sh install` makes a client key `relays` before Tor starts
and prints it once. `--open` keeps the old behaviour. I2P fronts have no client
authorization.

### 8. Logs

- The gateway logged "tunnel up/down" to the journal on disk.
- The relay logged front addresses and connect times to the user's journal.

Fix: gateway and relay units run with `RUST_LOG=warn`; the relay prints the
front address only at debug level; journald on core and fronts keeps logs in
memory only (`Storage=volatile`, old logs deleted); no core dumps
(`LimitCORE=0`, `kernel.core_pattern`).

Consequence: after a reboot there are no logs from before it.

### 9. Push tokens

Phone clients register a push token. The server can never use it (no network)
but stored it: a link from an account to a phone, on the core's disk.

Fix: `allow_pushers = false` (answer success, store nothing).

### 10. Level-2 windows and clocks

Each relay sent on multiples of the window by its own clock. A clock that is a
second off gives that device a stable offset a front can recognise. The core
has no time sync, so its grid could drift from the relays'.

Fix: `WELCOME` carries the gateway's time; relays align to it. Trade-off in
`phase2-protocol-spec.md` §4.

### 11. Recognisable traffic

Bursts on exact 15 s multiples (level 2) or a flat 10 KB/s (level 3). An ISP
can tell that a line runs this software. Not fixed; now stated as a limitation.

### 12. Leaks around the relay

- Calls go direct (WebRTC/STUN). The server can't see or stop them in
  encrypted rooms.
- Integration managers get the user's Matrix ID through an OpenID token.
  Fix: `allow_openid_tokens = false`.
- Device names ("Element Desktop: Linux") are visible to other members. Open.

### 13. First SSH over clearnet

`setup-core.sh` and `setup-front.sh` are run over normal SSH first. The
provider sees the admin's IP address. Use `torsocks ssh` (or SSH over a VPN you
trust) for that first session too, and for the provider's web panel.

## Low items

- **L1** RocksDB marks deleted keys; the bytes stay in its files until
  compaction, and in any backup or disk snapshot. Clients also keep their own
  copies of messages.
- **L2** `install` no longer makes an ingress key. Make one per front:
  `setup-core.sh add-client <name>`.
- **L3** continuwuity's socket now belongs to group `matrix-sock` (gateway
  only) while port 80 is closed. `direct-ingress on` switches it to Tor's group
  and restarts continuwuity.
- **L4** Tor may attach several streams for the same onion to one circuit. The
  spec (§6) assumes one circuit per relay connection. Check with real Tor.
- **L5** No `update` command; no unattended upgrades over Tor.
- **L6** `cargo audit` (2026-11-10): nothing for the tunnel. The server
  lockfile has upstream advisories (quinn-proto, rustls, rsa, pulldown-cmark,
  crypto-bigint, ctutils, libz-sys), mostly in network code this setup does
  not use. Not analysed one by one.
- **L7** The kit binaries are built by hand. Build them yourself or in CI.
- **L8** Tor enforces client authorization only while at least one client is
  listed. `remove-client` of the last key therefore opened the ingress onion
  (and a front's onion) to anyone who knew the address; so would an install
  without a first key. Fix: when no client is left, the scripts list a key
  whose private half is thrown away (`locked.auth`), so nothing can connect
  until the next `add-client`. The last admin key can't be removed.
